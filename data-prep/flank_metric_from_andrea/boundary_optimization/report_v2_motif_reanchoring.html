The Motif-Reanchoring Boundary Rule: Does It Actually Help?

Testing a specific new extension rule against real HG002 reads across 13 known disease loci

Generated 2026-07-31 · follow-up to report.html in this same directory · tandem-repeat-explorer / data-prep / flank_metric_from_andrea / boundary_optimization

Bottom line. The rule as originally specified (extend past any gap with ≤1/3 mismatches, anchored by one exact motif-unit match) makes real EH genotype quality worse at 10 of 13 tested loci and better at only 3 (RUNX2, ARX_2, EP400) — it is too permissive for short/degenerate motifs, where a matching 3-mer occurs by chance often enough to falsely "anchor" an extension into genuinely non-repeat flanking sequence. The fix is simple and well-supported by the same data: tighten the gap-mismatch threshold from 1/3 to about 0.15. At that threshold, 11 of the 12 problem extensions vanish entirely (the locus correctly stays at its current boundary) while the one genuine, quality-improving extension (RUNX2) survives untouched — because its accepted gap has a mismatch fraction of exactly 0.000, in a completely different class from the 11 false positives (0.167–0.267). Update (§9–10): re-testing the corrected thresholds on two independent broader, non-curated samples — a random TRExplorer v1 slice, and a slice specifically ranked by how repetitive the flanks already look — both found a messier picture with no locus feature that separates good extensions from bad ones. The curated-locus result above should be read as a best case, not a representative one. Total Hail Batch spend: $0.174 of the $10 budget ($0.0114 rounds 1–2, $0.0842 on a round-3 run cancelled after a ploidy bug was caught mid-run, $0.0464 on the corrected re-run, $0.0316 round 4).

1. The rule as specified

Per your instructions, for each side (left/right) independently: scan outward in whole-motif-unit steps looking for the next exact copy of the motif. Accept a jump out to that copy (encompassing the gap in between) if the gap's Hamming distance to a perfect in-frame repeat is ≤ 1/3 of the gap length — where the gap length is always a whole multiple of the motif length, per your clarification. Keep scanning outward as long as the cumulative gap fraction from the last accepted point stays ≤1/3; stop the moment it's exceeded without having found an anchoring exact copy. Implementation: motif_reanchor_extension.py, reusing boundary_metrics.py's already-validated per-position phase logic rather than re-deriving the (easy to get subtly wrong) reversed-coordinate math for the left side.

5. Root cause: the rule is chasing chance matches

Looking at the exact mismatch fraction of each accepted gap (threshold was 1/3 = 0.333):

HOXA13_3(right), NIPA1(right)NGC/GCG15–24bp4–60.250–0.267
RUNX2's accepted gap is a perfect (0-mismatch) continuation. Every other accepted gap has a real, nonzero mismatch rate (0.167–0.267) — comfortably under the 0.333 threshold, but not remotely "clean." For a short motif (most of these are 3bp, several are IUPAC-degenerate NGC/GCN which match 2 literal bases + a free wildcard), a coincidentally-exact 3-mer match is common: a random 3bp window matches a specific 3bp target with probability roughly 1/64 for a literal motif, and much higher (~1/16) for an NGC/GCN motif where 1 of 3 positions is a free wildcard. Scanning several units out from the boundary, hitting at least one such lucky match is not rare — and the loose 1/3 gap tolerance lets the rule "explain away" the real mismatches in between as tolerable noise, when they're actually the flank telling you it's not repeat-like anymore.

6. The fix: tighten the threshold

Swept the threshold (and, separately, requiring 2 consecutive exact units instead of 1 to anchor) across the same 64-locus set:

ConfigurationLoci extendedTotal extensionWhich loci
Original: threshold=0.333, anchor=1 unit12/64195bpall 12 from section 3
threshold=0.20, anchor=1 unit1/649bpRUNX2 only
threshold=0.10, anchor=1 unit1/649bpRUNX2 only (identical to 0.20)
threshold=0.333, anchor=2 units4/64189bpARX_1 (now 120bp!), HOXA13_3, ATXN3, RUNX2
threshold=0.20, anchor=2 units1/646bpRUNX2 only
Requiring 2 consecutive anchor units while keeping the loose threshold makes things worse, not better — ARX_1's spurious extension balloons from 12bp to 120bp, because a single lucky match no longer stops the scan early, so it searches further out and sometimes finds an even more distant (equally spurious) double-match. Tightening the anchor count is not a safe fix by itself; tightening the threshold is.
threshold=0.20 (anchor=1 unit, matching the original rule otherwise) eliminates all 11 false positives and preserves the one genuine extension, with no new Hail Batch run needed to confirm it: "don't extend" is exactly the baseline definition already tested in section 4, and RUNX2's specific accepted region is byte-for-byte identical between threshold 0.333 and 0.20 (its gap fraction is 0.000, nowhere near either threshold). So the quality data already collected fully validates the adjusted rule: 11 loci stay at their (already-measured, unchanged) baseline quality, and the 1 that still extends (RUNX2) is the one confirmed improvement.

7. Side finding: an IUPAC bug that inflated RFC1's apparent impurity

While building this analysis, RFC1 (motif AARRG, R = A-or-G per IUPAC) kept showing a reference purity of exactly 0.600 — suspiciously exactly 3/5. The cause: boundary_metrics.py's purity/hamming functions only special-cased literal 'N' as a wildcard, not other IUPAC ambiguity codes. RFC1's real reference sequence is a textbook-perfect tiled AAAAG repeat; compared literally against AARRG, the two R positions always mismatch (since real DNA is never literally the character 'R'), capping purity at exactly 3/5 regardless of true sequence quality.

Fixed generally: boundary_metrics.py now has a full IUPAC ambiguity table (R, Y, S, W, K, M, B, D, H, V, N) used consistently by both the purity/hamming and edit-distance functions. RFC1's corrected core purity is 1.000, not 0.600. This doesn't change the motif-reanchoring rule's conclusion for RFC1 (still 0bp extension, correctly — RFC1's real difficulty is its intrinsic AAAAG/AAGGG/etc. motif heterogeneity, not a boundary or purity problem), but it corrects a specific claim in the original report.html that characterized RFC1's reference purity as low (0.6) evidence of impurity, when it was actually a measurement artifact. Note EH's own RepeatPurity.cpp has the same literal-character limitation (its docstring: "an 'N' counts as a mismatch") — so ExpansionHunter's own reported ReferenceRepeatPurity field for RFC1 in its output JSON will still show 0.600; the fix here is a deliberate improvement over EH's own convention for analysis purposes, not a reproduction of it.

8. How this relates to the purity≥0.90 rule from report.html

The original report recommended extending a boundary until full-region reference purity (core + everything added so far) drops below 0.90. That rule is inherently self-limiting for short motifs: a single mismatch immediately after a long, already-pure core barely moves the full-region average, so it tends to extend cautiously and gracefully degrade. The motif-reanchoring rule instead looks at the local gap in isolation and is willing to "jump over" a bad patch entirely if a clean unit reappears soon enough — which is a reasonable idea (EP400's real interruption is exactly this shape) but, at 1/3 tolerance, jumps over patches that are bad enough to matter. The corrected (0.20 threshold) version of this rule and the original purity≥0.90 rule now agree closely in practice: neither recommends extending C9ORF72, RFC1, or BEAN1, and both point toward extending EP400 to (approximately) its current wider definition. The main remaining difference is EP400's exact right-side stopping point and RUNX2, where the motif-reanchoring rule (correctly, per section 4) finds a small real extension the purity-threshold rule found too via a different mechanism (see report.html section 8/9's RUNX2 discussion).

9. Round 3: a ploidy bug, and a messier result on the broader TRExplorer v1 set

You asked to redo the threshold comparison (0.15 vs. 0.20) on the broader TRExplorer v1 sample rather than just the 13 curated disease loci above, to check whether §6's clean separation generalizes.

A ploidy bug, caught mid-run

While this round's Hail Batch job was hanging on a chrY locus (no log progress for 9+ minutes), found the cause: the validation scripts (this report's §4 and the earlier round-2 run) passed --sex female for HG002 — but HG002 is the male child of the Ashkenazi trio. This project's own canonical scripts (run.sh, run2.sh) correctly use --sex male; only this analysis's own scripts had it wrong. Wrong ploidy silently forces a 2-allele diploid model onto chrX/chrY loci that are actually hemizygous in HG002 — affects every chrX/chrY locus tested so far, which in this dataset means ARX_1 and ARX_2 (both chrX) from §4's table. Cancelled the stuck run ($0.0842 spent, wasted — the job was stalled specifically on the mis-ploidy'd chrY loci) and reran with --sex male.

Broader validation: 98 TRExplorer v1 loci, 70 threshold-disagreements

Swept both thresholds across the ~20,000-locus stratified TRExplorer v1 sample (tier 3): 98 loci get nonzero extension under threshold 0.15 or 0.20, and of those, 70 disagree between the two (0.20 extends further or differently than 0.15). Built a validation catalog of baseline + both threshold variants for these 70 loci (plus the 4 ARX_1/ARX_2 male-fix entries above, 201 catalog entries total) and ran it through Hail Batch (analyze_round3_threshold_sweep.py). 1 locus's extended region exceeded 2x read length and was skipped by EH (same expected behavior noted in earlier rounds); 1 more had no genotype call at either threshold. 69 loci scored.

The clean separation from §6 does not generalize. On this broader, non-curated locus set: at threshold 0.15, only 1 of 69 loci gets extended at all — and that one is a real loss (ΔpOk −0.297). 0.15 is "safe" here only in the trivial sense that it almost never fires, not because it's correctly discriminating. At threshold 0.20, 63 of 69 loci get extended: 33 improve (sum ΔpOk +4.15) and 29 get worse (sum ΔpOk −3.83) — a roughly even split in both count and aggregate magnitude, i.e. close to a coin flip on this locus set. Unlike §5's clean story for the 13 curated disease loci (where every false positive was a short/IUPAC-degenerate 3bp motif), motif length does not separate winners from losers here: both the worst regressions and the biggest improvements are dominated by 5–6bp motifs in roughly equal proportion. Interpretation. The 13-locus curated disease set in §4–6 gave a clean, well-supported story: a specific, identifiable failure mode (short/IUPAC-degenerate motifs producing chance 3-mer matches) explained every false positive, and tightening the threshold fixed all of them while preserving the one true win. 10. Round 4: ranking by flank repetitiveness doesn't help either

§9 found no locus property that separates the reanchoring rule's winners from its losers on a broad, non-curated sample. The natural next test: what if we specifically target loci whose flanks already look the most repetitive — using Andrea's own flank_motif_similarity_left/ _right columns (how closely the flank matches a perfect in-frame repeat of the locus's own motif) — rather than an arbitrary catalog slice? These should be the strongest candidates for genuine under-extension.

Sorted the full 415,527-locus catalog by max(flank_motif_similarity_left, flank_motif_similarity_right) descending (sort_catalog_by_flank_repetitiveness.py), took the top 20,000, and re-ran the free local extension scan at thresholds 0.15/0.20 (scan_top20k_flank_repetitive_extensions.py).

Flank similarity barely enriches for loci the rule actually extends. Only 534 / 20,000 (2.7%) extend at 0.20 and 111 (0.6%) at 0.15 — essentially identical to the extension rate on an unranked, random-order 50,000-locus slice of the same catalog tested earlier (2.70% / 2.12%). The rule's actual trigger — finding an exact in-frame motif copy within a low-mismatch gap, immediately adjacent to the boundary — is a much narrower condition than "the flank's best-matching window looks similar to the motif." A locus can score high on flank_motif_similarity without having a clean exact anchor point nearby, so this intuitive heuristic doesn't concentrate the rule's true positives (or false positives) any better than chance.

Built a validation catalog for the 534 extended loci (1,070 entries after dedup, build_flank_repetitive_validation_catalog.py) and ran it against real HG002 reads via Hail Batch (run_hail_validation_4.py, --sex male used correctly from the start this time). This reinforces, rather than resolves, §9's open question. Two independent non-curated samples now (a random TRExplorer v1 slice in §9, and a flank-similarity-ranked top-20k slice here) both show the same pattern: no locus-level feature examined so far (motif length, flank_motif_similarity, or which one triggered the extension) predicts whether a given motif-reanchoring extension will help or hurt genotype quality outside the curated disease-locus set. The curated 73-locus result from §4–6 remains the cleanest evidence this rule has, and it remains an outlier compared to every broader test run since.

11. Recommendation

The threshold=0.15–0.20 fix (§6) is well-supported for known disease loci specifically, but §9–10 show it does not generalize cleanly to the genome at large — do not apply this rule at catalog scale without further work. On the curated 73-locus disease set, tightening to ~0.15–0.20 cleanly removed every false positive while keeping the one true win (RUNX2), and that result still stands. On two independent broader, non-curated samples — a random TRExplorer v1 slice (§9) and a flank-repetitiveness-ranked slice (§10) — the same thresholds behave very differently: 0.15 rarely extends anything and what it does extend is a mixed bag; 0.20 extends much more but is roughly a coin flip on the random sample and net negative on the repetitiveness-ranked one. No property identified so far (motif length, flank_motif_similarity) predicts which extension will help or hurt. Recommended scope: apply this rule (threshold ≈0.15–0.20) to hand-curated/disease-associated loci where the §4–6 evidence directly applies; do not extrapolate it to catalog-wide automated boundary correction without identifying what actually separates good extensions from bad ones. Do not "fix" the anchor-count instead of the threshold — that made one disease-locus case (ARX_1) an order of magnitude worse (§6).
  • Threshold matters far more than anchor length for this rule's safety, at least on the curated disease-locus set.
  • Short and IUPAC-degenerate motifs are the highest-risk case for false "anchors" among known disease loci — but this specific failure mode does NOT explain the broader TRExplorer v1 or flank-repetitiveness-ranked sets' mixed results (§9–10), so it should not be treated as the general explanation for why this rule sometimes hurts. (Exception: §10 found the single most extreme false positive in this project on a 2bp dinucleotide motif, so degenerate short motifs are still worth extra caution even if they don't explain the whole picture.)
  • "Flank looks repetitive" (flank_motif_similarity) is not a useful pre-filter for this rule — it neither enriches for loci the rule extends (§10) nor predicts the outcome when it does (Spearman ≈ 0).
  • RFC1's reference purity should be recomputed with proper IUPAC handling anywhere it's used as a quality signal (section 7) — it is not, in fact, an impure locus by this metric.
  • Always pass the correct --sex flag for chrX/chrY loci — HG002 is male; using the wrong ploidy model inflates apparent CI width/instability for hemizygous loci in a way that looks like, but is not, a real quality problem (§9).

12. Limitations

  • threshold=0.20's validation on the 13-locus disease set reused already-collected data rather than a fresh Hail Batch run (the specific accepted/rejected outcomes were identical to what was already measured). §9's fresh, larger run on TRExplorer v1 confirms this caution was warranted — the clean 13-locus result did not hold up on a broader live test.
  • Single-sample (HG002) validation throughout — 13 curated loci in §4–6, 69 broader loci in §9. A locus-count and sample-count large enough to fit a proper ROC-style threshold curve (rather than picking a threshold by eye) is a reasonable follow-up, especially given §9's finding that the winning/losing split on the broader set isn't yet explained by any tested locus property.
  • Compound loci (9 of 73) were excluded entirely, not handled properly (e.g. by using the full multi-region span) — some of them (ATXN8OS, FRA10AC1, HTT, TMEM185A) did show nonzero extension under the original threshold, but that likely reflects the rule reabsorbing the locus's own adjacent sub-region rather than a real test case, so they were left out rather than reported unreliably.
  • pOk was used as the single quality signal for consistency with the original report's methodology; a genotype-vs-truth comparison (where truth is available) would be a stronger signal than a before/after confidence metric on the same unknown-truth sample.
